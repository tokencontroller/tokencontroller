# How the service closes periods and serves reports

This fills in the Bills, Approval, Cadence and token sheets, Monthly close, Adjustments, Reports and Exports pages and ADR 0007 where the service in `apps/server` needed details. The core's part is ADR 0016.

- **A bill is one organization, period, provider and cost source.** Sending it again with the same figures changes nothing; different figures make a new revision. A closed period keeps the revision it closed with, and a newer one shows as restated. `provider` names who charged, such as `anthropic` or `cursor`. Discount and credit are positive amounts taken off gross; gross may be left out and is then net plus discount plus credit.
- **Only metered cost sources have bills.** Seat and subscription usage is shown as an estimate next to the reconciliation and stays off the cost sheet, as the Bills page says, so the service hands the core no block without a bill.
- **A token entry is charged on its provider's bill.** With several bills from one provider in a period, the token entries go on the first by cost source, in the order the Bill schema lists them; the other bills have only residual.
- **Exchange rates are the European Central Bank's reference rates.** The `exchange-rates` job in the job runner (ADR 0002) stores them per day. A bill without a rate gets the rate of the period's last day. Token entries in a bill's currency convert at that bill's rate; any other figure converts at the period's last day, or today while the period runs. A day without a published rate uses the latest earlier one, up to ten days back. `TC_PRICES_REFRESH=off` also stops the daily rate refresh.
- **The close is one database transaction.** It refuses a period that has not ended, one already closed, and with approval on, one with a submitted or rejected token entry. On a metered cost source it also refuses while a provider with counted token entries has no bill for the period. It locks every token entry it counts, writes the bills and rates it used, and keeps the price table and tag map versions. Database triggers refuse any change to a locked token entry, its splits and their tags.
- **A token entry submitted for a closed period becomes a late adjustment per split.** Each carries the split's tags and its value at the closed period's rates, and the token entry is locked. Nobody posts it by hand, so it carries no person.
- **An adjustment is posted by a controller to a closed period only**, in the reporting currency, with tags, a reason, their name and the time. It is never zero.
- **The cost sheet can be previewed while a period runs**, marked open. A link for finance holds a long random secret; the service keeps only its hash, and a controller can revoke the link.
- **A people manager approves and rejects token entries within the filters they are assigned, never their own.** A controller can decide any. Approving in bulk takes a filter and a period. A reject needs a reason, and a locked token entry cannot be rejected.
- **A person's cadence is the shortest that applies.** The organization's cadence and the cadences of the projects on their token sheets in the last 90 days apply. A cadence period starts on the day the cadence starts, by default the Monday of the week it is set. A custom cadence is 1 to 366 days.
- **Only people who have submitted a token sheet can be late.** A cadence period is late when it has ended and no token sheet overlaps it. An empty token sheet says there was nothing to report. The service looks back at most 60 cadence periods.
- **A token sheet submit covers every cadence period since the person's last token sheet**, up to the running one, plus the period of each token entry it carries. An empty submit still writes the token sheets, since an empty token sheet says there was nothing to report. Submitting from the CLI and from the web app is the same request.
- **A rejected token entry goes back to its agent manager as a draft once they fix it.** They fix its tags or split it into 2 to 20 shares that add up to 100 percent; the fix is placed by hand and wins over rules. A locked or approved token entry cannot be fixed.
- **Asking everyone to submit is one request per organization and period.** A controller sends it for a period not yet closed; asking again replaces it. The request comes with every person's context and token sheet until the period closes, for the Claude Code mod, the CLI and the web app to show.
- **A ticket key is unknown once a sync has run past the token entry and not found it.** The service marks the key only when every ticket system project the organization maps has synced after the token entry arrived. Placement then runs without that key, and the review list shows the token entry as unknown ticket. When a later sync finds the ticket, the token entry is placed on it again. A ticket named by hand stays named.
- **Reports group by any tag name, or by agent harness, agent name, model, effort, speed, day (in UTC) or cost kind.** The share view gives adjustments no share, since shares are shares of usage. Another currency converts at the rate of the period's last day. Signed-in people, the CLI and read tokens can read reports; service tokens cannot.
- **The API gives money as a decimal string in its currency, never a float, and shares in basis points.** Basis points add up to exactly 10,000 with the core's largest-remainder method, so a share view always comes to 100 percent.
- **Token budget vs actual is the core's comparison.** Actual is the list value of the counted splits the token budget's filter matches, plus the adjustments on that filter, in the reporting currency. A token entry on an unknown model leaves an underrun open but not an overrun, since its cost can only add.
- **A token forecast matches the ticket's title and description against the summaries of token entries in closed periods, by embedding.** Each summary is embedded once, in batches, by the model at `TC_EMBEDDINGS_URL`. The tickets of the closest token entries are shown with a confidence and their actual cost, and the proposal is their median cost. It becomes a token budget only when a person accepts it. Without that setting, or with forecasts switched off for the organization, nothing is proposed and nothing is sent.
- **Saved reports belong to the organization.** Everyone sees them, each with the cost their role covers; their creator or a controller removes one.
- **Outliers compare a ticket with the median of similar past tickets.** A ticket's cost is its cost in the period and the twelve months before. Similar past tickets are the same project's tickets of those twelve months, or the organization's when the project has fewer than three. The report ranks tickets by how many times above or below the baseline they are, so twice and half are equally far.
- **The raw export is a zip of JSON files**, one per kind of record, rows as stored with their children nested, and a manifest. Secrets are left out. Only controllers can download it.

## Why

The cost sheet goes to finance and the raw export is how an organization leaves, so both must hold exactly what was stored and add up without anyone fixing a figure by hand. Locks in the database itself make a closed period hold even against a bug in the service. Each choice above was the smallest one that keeps the docs' promises.
