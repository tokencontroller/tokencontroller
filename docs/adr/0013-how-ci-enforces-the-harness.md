# How CI enforces the harness and merges green pull requests

This fills in ADR 0003 and ADR 0011 where the code needed details.

- **Lint switches are caught in the source, not only by `forbid`.** `#[tokio::main]` and `#[tokio::test]` write `#[allow(clippy::expect_used)]` into the code they generate, and `sqlx::query!` writes `#[allow(clippy::unreachable)]`, which a `forbid` level refuses to compile. So `expect_used` and `unreachable` are `deny` instead of `forbid`, and `scripts/harness_check.py` fails CI on any `allow`, `expect` or `warn` lint attribute in our own Rust code, also inside a `cfg_attr` spread over several lines. Every other lint ADR 0003 names stays `forbid`.
- **The lint block also forbids the crash points and dropped errors ADR 0003 did not name.** `unreachable!`, slicing a string (it crashes inside a multi-byte character) and throwing an error away with `.ok()` fail the build like `unwrap` does.
- **Nothing outside the lint block can switch it off.** Every Rust package is a member of the root workspace and has exactly `[lints] workspace = true`. Cargo config files (`.cargo/config.toml`) are not allowed, because they can pass compiler flags, profiles and lint levels around the lint block. `clippy.toml`, `rustfmt.toml` and `rust-toolchain.toml` exist only at the root.
- **The harness guard protects what exists.** Changing or deleting a harness file that is already on `main` (the lint block and profiles in `Cargo.toml`, `clippy.toml`, `deny.toml`, `rust-toolchain.toml`, `rustfmt.toml`, `.config/nextest.toml`, `.cargo/mutants.toml`, the workflows, the harness scripts, the golden cases) fails CI unless the pull request has the `harness-change` label, and CI checks that the maintainer set it. Adding a new golden case or a new workflow needs no label, so new checks can land while agreed ones cannot be loosened.
- **The test count is counted in the source, and every counted test must run.** CI counts test functions and golden case folders on the pull request and on its base, and fails if either drops. After the tests, CI fails if nextest ran fewer tests than the source holds, so a test file left out of the build cannot count. `#[ignore]`, `#[should_panic]` and always-false `cfg`s such as `#[cfg(false)]` fail CI.
- **Mutation testing blocks the merge.** On every pull request that changes `crates/core`, `cargo-mutants` mutates the changed lines and CI fails when a mutant survives. The nightly run still covers the whole crate.
- **The service runs only SQL the compiler checked (ADR 0005).** Code under `apps/server/src`, outside its test modules, may not call sqlx's runtime query functions, use the query builder or the unchecked macros, or hand SQL text to an executor.
- **Green pull requests merge themselves.** When every CI job passes, CI squash-merges the pull request, only if its head is still the commit that was tested, then starts CI on `main` so the image is published. The `hold` label stops this for one pull request.

## Why

A forbid level that breaks the standard async test macro would push every async test into hand-written runtimes; one line of grep keeps the same guarantee. Requiring the label for new files would make every new golden case wait on the maintainer, who does not review code. Counting tests in the source keeps CI fast and still catches deleted tests. A package without the lint table, or a Cargo config file, would switch the whole lint block off without touching a harness file. Pull requests merge themselves, so mutation testing that only runs at night would block nothing.
