Rules set the tags of token entries: their ticket and project, and any other tag, such as purpose: code-review for sessions on a review/ branch. They work like the rules in a banking app: set once, every new token entry lands where it belongs, and people only handle the exceptions.

Signals

A signal is a fact about a session that hints at where its cost belongs:

  • the branch and the working directory
  • the repository
  • the pull request number
  • the subagent type
  • ticket keys that match a project's ticket key pattern, found in your prompts, the session title or the pull request title

Prompts and titles are read on the machine. Only the ticket keys found in them leave it, as Security and privacy lists.

Where rules run

Rules run twice.

  • On the machine. The Claude Code mod, the CLI and the GitHub Action know your rules and ticket key patterns, but not your tickets. They read the signals, including prompts and titles that never leave the machine, and send each token entry with the ticket key they found.
  • In Token Controller. The service knows your tickets from your ticket system. It checks every ticket key against them, runs the rules again on the signals it received, and tries a summary match for token entries that still have no ticket.

Token entries from the token entries endpoint or a CSV import only go through the second pass.

Order

Each token entry goes through these steps, and the first that finds a place wins:

  1. A ticket named in the token entry. Picked by hand in the mod or the CLI, passed to the GitHub Action, or sent in the ticket field.
  2. Rules that find a ticket. By default: the ticket key in the branch, then in the pull request title, then in your prompts or the session title.
  3. Summary match. See below.
  4. Rules that place on a project, such as the repository rule.
  5. Unattributed. See below.

Within a step, organization rules run before personal ones, so a person's own rules only handle what the organization's rules leave open.

When prompts name several tickets

By default the ticket named most often in your prompts wins, and on a tie the latest one. An organization can switch this to an equal split between the tickets, or to the first one named.

A mention is not work. "The follow-up ticket will be KD-260" names a ticket the session did not work on. Rules cannot tell the difference. The classifier can, and you can always place a token entry by hand.

Summary match

When no rule finds a ticket, Token Controller compares the token entry's summary with the titles of open tickets, in the project the repository maps to or, without one, in the whole organization. If one ticket clearly fits, the token entry is placed on it and marked matched by summary in the review list and in reports. If none clearly fits, the next step runs. An organization can switch summary matching off under Rules.

When rules change

A new or changed rule runs again over the token entries of every open period, so a fix also reaches past work. Token entries placed by hand keep their place. Closed periods are locked and never change; correct them with an adjustment.

When nothing matches

The token entry stays unattributed and shows up in your review list. The share placed by rules is your attribution; you set the attribution target.
