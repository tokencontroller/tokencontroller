Concepts

Token Controller is cost accounting for AI agents, with management control on top. This page explains the ideas the rest of the docs build on. Every term is defined in the glossary.

Two sides that must match

As in double-entry bookkeeping, there are two sides, and they must add up to the same total.

SideWhat it is
Token entriesEvery agent session produces one: tokens, cost, model, agent harness, start and end time, a summary, and the ticket or project it was for. Token Controller collects these.
BillsEach provider sends one figure per period for the whole organization, with every client and project mixed together. Only metered usage is on it: tokens and per-call fees. Seats and other flat fees are not.

Once the token entries add up to the bill, the bill can be split down to the work that caused it. The check runs per bill, and the organization total adds them up. What no token entry explains, such as usage in the provider's own chat app, shows as residual.

Some token entries arrive automatically: cloud agents, CI agents, a support agent that answers email, and telemetry. Telemetry brings the money but not the ticket or the summary. Those come from the person who ran the session, on a token sheet, the way hours go on a timesheet.

On a seat plan (Claude Team, Max, Pro) there is no usage bill. Token Controller then shows what the usage would have cost at API prices, labelled as an estimate on every figure, and every report can switch to the share view: percentages of the period instead of money.

Every cost is booked twice

A timesheet books hours both to a person and to a ticket. Token Controller does the same with cost. Both come from tags on the token entry, such as person: mara, ticket: KD-214 or team: web.

Booked toAnswersHow it is built
Cost centerWho answers for it?Every token entry has exactly one agent manager. You are the agent manager of your own sessions. A tech lead is the agent manager of the CI automations they set up. By default the person is the cost center. People carry tags such as team: web, which their token entries inherit. An organization where teams answer for money maps the cost center to team.
Cost objectWhat did it pay for?The first rung of the ladder with a value: by default a ticket, then a project, then the organization. Tickets can sit inside other tickets, so a project's cost is the sum of its tickets. A client is a tag on projects, such as client: acme; an organization can add it as a rung.

The two sides are separate on purpose. A developer can work on three projects for three project managers and still be one cost center. Tech leads and heads of department read cost by person and team. Project managers, directors of delivery and account managers read it through tickets, projects and clients, whoever caused it.

Example. A PR review bot reviews a pull request for ticket KD-214. The cost sits with the tech lead who is the bot's agent manager (cost center) and shows on KD-214 as review cost (cost object). The ticket's assignee is not charged for it, but a ticket with expensive reviews is visible on its report.

When no ticket matches, the cost falls back to the project, then to the organization. What nobody tagged at all sits on the organization as unattributed. A token entry without an agent manager shows as an error to people managers until someone takes it.

Tags

Beyond person, ticket and project, an organization adds the tags it needs: team, client, feature, purpose. A token entry has one value per tag name, so cost by team or by client always adds up. A report is a saved tag filter, a token budget is money for a tag filter, and a people manager is assigned the filters they look after. Most tags come in on their own: from the person, the project, rules, a repository's config file or telemetry. See Tags and the tag map.

Example. An agency tags people with their team and projects with their client. Without anyone typing a tag, the account manager for Acme reads cost per team for client: acme, and the Web lead reads cost per client for team: web.

Agents

An agent is software that calls a model on a person's behalf and so costs money. A person typing in a provider's own chat app is not an agent; that usage shows as residual. Token Controller keeps no record of agents, only of the cost they cause. Each token entry names the agent harness (Claude Code, Codex), the model, and an optional agent name, a label such as "review bot" so the same automation on several projects can be totalled.

Cost kinds

Every token entry carries one cost kind, as the built-in tag kind.

Cost kindMeaning
DirectPlaced on a ticket.
Project overheadProject work that belongs to no single ticket, such as research, discovery or setup.
Organization overheadWork that belongs to no project, such as dependency updates or internal tooling, when nobody made a ticket for it.
PersonalA person's own learning and experiments.
UnattributedSpend that no rule or person has placed yet. Always shown as its own line. Overhead is a choice; unattributed is the absence of one.

Every token, accounted for

All of the bill is always accounted for. Whatever is not placed shows as unattributed, and whatever no token entry explains shows as residual. Neither is ever hidden.

Attribution is the share a rule or a person has placed, with any cost kind. Personal and overhead count; only unattributed does not. Your organization decides which tags must be filled to count: a project is enough for some, others want every session on a ticket, or also a purpose. Expect 70 to 80 percent at first, improving month by month. Each organization sets its attribution target; the default is 80 percent.

Every figure says what it is: billed, a list-price estimate, or an unknown model.

The loop

On top of the accounting sits the classic budgeting loop: plan, record, reconcile, learn.

  1. Plan.

    A token budget on a person (for example 1,500 EUR a month), a ticket, a project, a team or any other tag filter, for a period. You type it, or accept a token forecast: what similar past work cost, found by comparing the ticket with the summaries of past token entries.

  2. Record.

    Token entries come in, automatically or on token sheets.

  3. Reconcile.

    Rules tag each token entry with its ticket or project, people review and submit, the bills come in and both sides are checked against each other, the month is closed.

  4. Learn.

    Actual against token budget, per person, ticket, project or any tag. Overruns and underruns both get a look. An overrun may be a problem. An underrun may mean someone can teach the others, or that the next token forecast should be lower. History feeds the next token forecast, so a new client project can be quoted from what similar work cost before.

Every part of the loop is optional. You can use Token Controller only to collect token entries and match them to the bill, and add token budgets later. A token budget never stops spending; there are no spend alerts and no spend caps.

Where Token Controller ends

Token Controller ends at the cost sheet: the locked account of one closed period. Charging a client for what is on it (pass-through) happens in your own invoicing tool.

Any provider, any agent

Providers charge in several ways: subscriptions, seats, usage at API rates, API keys, cloud marketplaces (Bedrock, Vertex, Foundry) and tools that resell model usage. Token Controller treats them all the same way; a bill exists for the metered ones. Every organization has one reporting currency; a bill in another currency is booked at the exchange rate of its date, and any report can be shown in another currency.

Coding agents came first because their session files sit on the developer's machine. Any agent that can report home works, including remote and support agents.

Local first

The CLI is fully useful with no service connected, including an export for reporting by hand in a spreadsheet. The local tool and the service talk over a documented protocol, so the local tool can connect to any compatible service, or none. Transcripts never leave the machine.
